Architectural Design for a Unified Local Situational Awareness and Information Desk ServiceThe development of a unified local situational awareness service requires a multi-faceted systems architecture capable of high-frequency telemetry processing, low-latency audio distribution, and the synthesis of disparate public data feeds. This report provides a comprehensive design for a web-based information desk, tailored for use in the Tualatin, Oregon, region, integrating Software Defined Radio (SDR) data acquisition with real-time infrastructure and emergency information. The proposed system utilizes containerized microservices to ensure modularity, scalability, and resilience in a local deployment environment.Foundational Architecture and SDR Data AcquisitionThe cornerstone of the situational awareness service is the ingestion of real-time telemetry from local radio frequency (RF) sources. This is achieved through a stack of containerized applications that interface with low-cost SDR hardware to track aviation (ADS-B) and maritime (AIS) traffic, alongside digital public safety radio (P25).ADS-B Ingestion via UltrafeederThe aviation tracking component is centered on the "ultrafeeder" container, a sophisticated wrapper for the readsb decoder. This container serves as the primary ingest point for 1090MHz Mode S Extended Squitter signals. The architecture leverages a minimalist setup for high-efficiency deployments, particularly when resource constraints on edge hardware are a factor. By setting environment variables such as TAR1090_DISABLE=true and MLATHUB_DISABLE=true, the system can be configured to focus solely on raw data acquisition and distribution to a central dashboard, reducing overhead associated with local visualization if a unified map is used instead.For reliable hardware identification, the design utilizes the READSB_RTLSDR_DEVICE variable to target SDRs by their serial number. This is critical in a multi-SDR environment where several dongles compete for USB bus resources. The system also incorporates tmpfs volumes for high-frequency input/output operations, such as temporary JSON state files, to protect the longevity of flash-based storage media. Unlike the standard aircraft.json file which is typically polled every second, the position port outputs a new JSON object for every aircraft position received, enabling sub-second fluid movement on the dashboard map. The use of jemalloc preloading within the container further optimizes memory management, reducing the overall footprint of the aviation tracking stack.Maritime Surveillance with AIS-catcherMaritime situational awareness is provided by AIS-catcher, a dual-channel AIS receiver that decodes VHF signals at 161.975 MHz and 162.025 MHz. The service architecture defines AIS-catcher using a JSON-based configuration, which allows for precise control over receiver parameters and output channels. For this application, the JSON_FULL output format is mandated, as it provides a fully decoded representation of maritime messages, including static vessel data and voyage-related information.The importance of the JSON_FULL format lies in its comprehensive data fields, which are compatible with legacy tools like gpsdecode. This allows the information desk to display not only the position of a vessel but also its identity and status. This creates a logical bridge between the ADS-B and AIS feeds, allowing the system to track a Coast Guard helicopter through both aviation and maritime data streams simultaneously, ensuring no loss of coverage during critical operations.Digital Radio Integration and Audio Streaming DesignA central requirement for the local information desk is the integration of real-time audio from public safety agencies. This is accomplished using OP25, a software suite designed for decoding APCO P25 digital radio systems commonly used by police and fire services in the Washington County and Tualatin Valley region.OP25 Signal Processing and MetadataThe design utilizes the multi_rx.py application within the OP25 suite, which enables the monitoring of complex trunked radio systems using one or more SDR devices. The system architecture specifies that each SDR device must be assigned a unique serial number using rtl_eeprom to prevent device conflicts and ensure stable frequency compensation (PPM) values.Audio data is handled through a low-latency UDP pipeline. OP25 decodes digital voice frames into raw audio packets, which are then transmitted to a local or remote UDP port. A critical technical nuance in the OP25 architecture is the allocation of UDP ports in pairs; for instance, if the first channel is assigned port 56120, the second must be at least two ports higher (e.g., 56122) to prevent interference, as the system may reserve the port + 1 or port + 2 slots for control data or secondary time slots in DMR modes.ComponentPort / ProtocolFunctionalityVoice Channel (VC)UDP 23456Primary audio stream destination (default)Control Channel (CC)UDP 23450Metadata and trunking management dataWeb TerminalHTTP 8080Remote console for channel hold and lockoutLiquidsoapUDP / TCPTranscoding and relay to Icecast serverTo provide a professional user experience, the system must display metadata such as the active Talkgroup ID (TGID) and Alpha Tag (e.g., "Tualatin Fire Dispatch"). This metadata is sent in parallel to the audio stream. In advanced configurations, a PHP-based backend or a custom Python wrapper (such as audio.py) interacts with the OP25 web terminal via HTTP POST messages to request updates and issue commands like "hold" on a specific frequency during an active incident.Icecast Distribution and Web Audio ProtocolsThe audio stream is delivered to the final web dashboard via an Icecast server, which acts as an efficient multi-client relay for MP3 or AAC data. The integration between OP25 and Icecast is facilitated by Liquidsoap, a versatile media toolkit that captures the UDP audio from OP25, normalizes the levels, and pushes the stream to an Icecast mountpoint.The Liquidsoap configuration (typically op25.liq) utilizes the input.external function to call audio.py, which bridges the UDP packets into the stream. For the web player to display real-time metadata, the system implements the Icecast "Icy-Metadata" protocol. This parser reads the stream, extracts the metadata blocks, and updates the dashboard UI without interrupting the audio playback. This ensure the user sees "Engine 211 En Route" simultaneously with the audio confirmation.Environmental and Public Infrastructure IntegrationThe information desk synthesizes real-time sensor data with asynchronous public API feeds to provide a comprehensive view of the local environment.Local Weather and Hazardous AlertsThe service integrates weather data specifically for the Tualatin Valley area using the National Weather Service (NWS) API. The design pulls current observations from local airport weather stations, such as Aurora State Airport (KUAO) and Portland-Hillsboro Airport (KHIO), which are proximate to the Tualatin area.Beyond basic temperature and humidity, the system prioritizes "Hazardous Weather Conditions." This includes frost advisories, freeze warnings, and flood alerts, which are extracted from the NWS MapClick feeds. These alerts are time-stamped and presented as high-priority notifications on the dashboard. This allows the information desk to serve as a predictive tool, alerting the user to upcoming rain or freezing conditions that might impact local travel or infrastructure.ODOT TripCheck and Traffic MonitoringThe Oregon Department of Transportation (ODOT) TripCheck API provides a deep inventory of traffic and roadway data essential for a regional situational awareness desk. Furthermore, the CCTV inventory includes images from partner agencies, ensuring that city-managed cameras in Tualatin are integrated alongside state-managed highway cameras.Utility Status and PGE Outage MappingIn the event of severe weather or equipment failure, power outage information is a critical data point. While Portland General Electric (PGE) does not provide a simplified public JSON API for all outage events, the system utilizes "Git scraping" and map backend ingestion to track regional outages. The architecture monitors the PGE Outage Map for polygon and point data representing reported failures.The system focuses on the following PGE data structures for Tualatin:Outage Polygons: Large-scale areas without power, which are more indicative of feeder line or substation failures.Outage Points: Individual events, often tagged with the cause (e.g., "Trees," "Scheduled Maintenance") and the estimated time of restoration (ETR).Customer Authorizations: For commercial sites, the design can leverage the PGE "Share My Data" API, which uses the OAuth 2.0 protocol and ESPI standards to provide detailed energy usage and billing data to authorized third parties.Emergency Alerts and Community InformationThe human element of situational awareness is satisfied by integrating news and official alerts from local government and media organizations.FlashAlert Newswire and Regional Emergency NetworksThe primary mechanism for emergency information distribution in the Pacific Northwest is the FlashAlert Newswire. This system is used by school districts, police agencies, and municipal governments to push news releases and emergency closures. The information desk subscribes to the "Portland - Longview to Salem" region, which covers the Tualatin area.FlashAlert provides several integration paths:XML Data Feeds: Participating media (and professional dashboards) can receive XML files every 15 minutes containing the latest closures and news releases.Web Monitoring: The service monitors regional report pages which update within one minute of information being received by the media hub.Push Notifications: The FlashAlert Messenger app uses a subscription-based model to deliver instant notifications for specific organizations, such as the Washington County Sheriff's Office (WCSO).The system automatically parses WCSO news releases for high-priority keywords such as "Assault," "Arrest," or "Missing Person" to generate immediate visual alerts on the dashboard.Local News and Municipal FeedsCommunity context is provided by the City of Tualatin and local publications. The City of Tualatin offers several RSS feeds for website updates, which the service polls to track city council meeting agendas, public works project updates, and library events.News SourceData TypeKey ContentTualatin TodayEmail / RSSMonthly digest of essential city newsCity of Tualatin NewsWebsite PollPolice enforcement missions, budget infoTualatin LifeLocal NewspaperPeople-centric features, school sports, businessWashington County EMEmergency ManagementMajor incidents, wildfire, HazMat infoThe Tualatin Life feed is particularly useful for identifying local trends and "Editor's Picks" that might not be captured in official government notices, such as new business spotlights or local environmental issues like the Nyberg Creek Trail Project.Network Security, Edge Exposure, and Service OrchestrationA professional systems design must account for the security and accessibility of the service, especially when it is deployed on a local network but needs to be accessible remotely.Container Orchestration with DockerThe entire stack is managed via Docker Compose, which ensures consistent deployment across different hardware platforms. Each service is isolated in its own container, with clearly defined port mappings and volume mounts. For instance, the ultrafeeder container is defined with specific environment variables for latitude and longitude to ensure the local tar1090 map is centered correctly upon startup.The design incorporates health checks that monitor the status of the SDR decoders and web servers. Using docker inspect and jq, the system can verify that the internal processes of the containers, such as Nginx or readsb, are running without "deaths" or high restart counts. This self-healing architecture is essential for a service meant to run 24/7 as a standalone information desk.Secure Remote Access via Cloudflare TunnelsTo expose the dashboard and its underlying data streams to the internet without the risks associated with port forwarding, the architecture employs Cloudflare Tunnels (cloudflared). This daemon establishes an outbound-only connection to Cloudflare's global network, creating a secure bridge for both HTTP (web UI) and TCP (raw telemetry) traffic.The implementation follows a multi-tunnel approach:HTTP Tunnel: Exposes the main dashboard and the OP25 web terminal. This is typically routed via a public hostname like desk.example.com.TCP Tunnel: Exposes raw telemetry streams (e.g., ADS-B or AIS data) to remote parent nodes or secondary analysis tools. This is configured using a dedicated cf-tun-netdata-tcp.service file on Linux.Security is further enhanced by integrating Cloudflare Access, which adds an identity-based authentication layer in front of the tunnels. This ensures that only authorized personnel can view the information desk or interact with the radio controls. The use of Nginx as a local reverse proxy allows for complex routing, where different sub-paths (e.g., /api/adsb, /api/weather) are directed to their respective containers while maintaining a single SSL-secured domain.Frontend Visualization and Data OrchestrationThe frontend of the information desk is the point of synthesis for all integrated feeds. It is designed as a high-performance single-page application (SPA) that manages multiple real-time connections.High-Frequency Mapping with MapLibre GL JSFor the geospatial display of aircraft and vessels, the choice of mapping library is influenced by performance requirements. The use of vector tiles allows for "semantic" styling, where aircraft icons can change color or size based on altitude or emergency status (e.g., Squawk 7700).Real-Time Communication PatternsThe frontend utilizes a hybrid communication model to balance latency and efficiency:WebSockets: Reserved for high-frequency, bidirectional data such as aircraft positions and OP25 terminal control. WebSockets maintain a persistent TCP connection, reducing header overhead to just 2-14 bytes per message.Server-Sent Events (SSE): Used for unidirectional updates like weather alerts, emergency notifications from FlashAlert, and news headlines. SSE is lighter on server resources than WebSockets and includes native "auto-reconnect" capabilities.Polling: Employed sparingly for low-priority, infrequently updated data such as the ODOT CCTV inventory or PGE outage status.This tiered approach ensures that critical emergency data is pushed to the user with sub-100ms latency, while background information is updated in a way that minimizes browser and server load.Comprehensive System Design SynthesisThe integration of these disparate services into a single "Information Desk" creates a powerful tool for local situational awareness. The architectural coherence is maintained through a strict adherence to containerization and standard protocols.Data Flow and Interaction ModelThe information desk operates on a "Sense-Process-Visualize" loop:Sense: SDRs capture RF signals for ADS-B, AIS, and P25. APIs poll NWS, ODOT, PGE, and FlashAlert.Process: Decoders (readsb, AIS-catcher, OP25) normalize raw data. The backend service (Node.js/Python) aggregates these feeds into a unified state object.Visualize: The MapLibre-based dashboard renders the state, with high-priority alerts (e.g., "Road Closure" or "P25 Emergency Button") triggering visual and auditory cues.The system's modularity allows for "helpful sources" to be added with minimal friction. For example, if the user wishes to add local river level sensors or municipal parking availability, these can be integrated as additional API polling modules in the backend and new layers on the MapLibre map.Scalability and Edge ResilienceBy using Cloudflare Tunnels and Docker, the service can be deployed in a "Split Architecture" if needed. A low-power sensing node (e.g., a Raspberry Pi) can be placed near an antenna on a rooftop to handle SDR decoding, while the more resource-intensive dashboard backend and Icecast server run on a dedicated server or in the cloud. The TCP tunnel ensures that the telemetry remains synchronized between these nodes without exposure to the public internet.Conclusion and Future OutlookThe proposed design for a unified local situational awareness and information desk service provides a robust framework for real-time monitoring and community awareness. By leveraging professional-grade decoders like Ultrafeeder and OP25, alongside reliable public data from ODOT and the NWS, the system transforms raw environmental data into actionable intelligence.The causal relationships between these feeds are clear: a weather alert for heavy snow (NWS) is followed by real-time road condition reports (ODOT), verified by local traffic cameras, and supplemented by audio from snowplow dispatch (OP25). The use of modern web technologies like WebGL, WebSockets, and secure tunneling ensures that this information is delivered to the user with the precision and security required of a professional systems architecture.Future enhancements could include the integration of machine learning for anomaly detection (e.g., identifying unusual flight patterns or maritime maneuvers) and the expansion of the "Helpful Sources" layer to include local citizen science data, such as air quality or noise pollution sensors. This architecture serves as a scalable foundation for any municipality or organization requiring deep, real-time insight into their local operating environment.
